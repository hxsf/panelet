# 为 Panelet 添加新硬件

当前实现只支持 NOTE4C，尚没有可直接填配置即完成接入的通用 board trait。本文是新增适配的实施流程；第一块新板需要同时完成[架构文档](architecture.md)列出的显示与平台边界提取。

## 1. 建立设备档案

先新增 `docs/devices/<device-id>/README.md`，在[设备列表](../devices/README.md)标为“规划中”或“适配中”。记录准确型号、PCB revision、MCU、Flash/PSRAM、供电、显示控制器与分辨率、输入和可选外设。未知字段明确写待确认。

每项硬件结论保留来源：官方资料、原理图、参考源码推断或实测。硬件参考快照放在 `3rd-res/` 并登记[来源清单](../../3rd-res/SOURCES.md)，保留原版权、许可和修改记录；缺少明确再分发权限时单独标注待确认，不套用 Panelet 的代码许可证。NOTE4 与 NOTE4C 必须各有证据；同系列外壳、相同接口或分辨率都不能证明时序兼容。

先定义恢复入口、备份大小、安全状态检查和允许的写入范围，再设计上板步骤。NOTE4C 的 16 MiB 备份和 `0x20000` app-only 地址只适用于其已核验布局，不复制到未知设备。

## 2. 定义构建与设备选择

当前 `.cargo/config.toml` 默认构建 ESP32-S3，`app/os/sdkconfig.defaults` 与分区 CSV 绑定 NOTE4C。新设备必须有可复现、显式的目标配置，至少包含 MCU/target、内存、SDK 配置、分区、显示描述、输入映射和板级电源策略。

接入第二块板时再建立 `boards/<device-id>/`，并把 NOTE4C 也迁入同一选择机制。构建时应拒绝未选择设备或选择冲突，不能让两个 board feature 同时使用同一批 GPIO。现有备份、刷写脚本尚不是通用工具；为新板扩展之前先为目标识别、镜像容量、分区与写入范围补充 mock 验证。

## 3. 适配显示与输入

新显示后端必须明确尺寸、支持颜色、像素编码、旋转、BUSY 极性/超时和刷新能力。若控制器不同，新增可主机测试的驱动 crate；原始指令与硬件时序留在驱动/board adapter，不进入脚本 API。

当前需要同时调整这些位置：

- `crates/ssd2683/src/framebuffer.rs` 定义固定 400 × 300、MSB-first 2 bpp 的 NOTE4C 缓冲区。
- `crates/panelet-ui/src/{lib,canvas}.rs` 直接依赖该缓冲区与四色 palette。
- `crates/panelet-rune-abi-poc/src/{mvp,os,display}.rs` 固定 Canvas 容量/颜色，DisplayBroker 使用 SSD2683 窗口类型。
- `app/os/src/editor/{runtime,transport}.rs` 与 `editor.html` 固定预览帧尺寸和解码方式。

先提取统一的显示描述和绘图目标，再增加黑白格式。颜色转换须有明确行为：拒绝不支持颜色，或采用文档化转换规则，不能静默把四色位值当成黑白像素。浏览器与原生预览使用相同设备描述和渲染规则。

`canvas.flush()` 保持提交画面的语义，由宿主选择呈现策略。新驱动没有实测局刷证据时只报告全刷能力；不要自动继承 NOTE4C 的 PTLW 指令、50% 面积阈值或周期全刷策略。刷新错误和超时均须尝试安全清理，清理失败也要向上报告。

输入适配把物理按键、触摸等转换成宿主事件。保留“采样不被长时间刷新阻塞”的边界，并明确缺少上/下/确认键时如何映射；不能要求所有硬件都具有 NOTE4C 三键布局。

## 4. 连接平台服务

| 服务 | 当前入口 | 新设备适配要求 |
|---|---|---|
| 引脚、供电、总线 | `app/os/src/board.rs` | 具体电平、复用和启动/关闭顺序集中在 board adapter；保留 ROM/USB 恢复路径 |
| Wi-Fi、HTTP、时钟、NVS | `app/os/src/server.rs` | 复用管理和宿主契约，替换平台实现；凭据更新继续采用验证后生效规则 |
| 存储 | `app/os/src/storage.rs`、`panelet-widget-store` | 区分挂载与格式化，核对文件名/容量/原子替换语义；不得因挂载失败自动格式化 |
| RTC、电池等硬件能力 | board adapter 与 Rune HostIo | 缺失或未实现的能力返回明确 `unavailable`，不填虚构数据 |
| 蓝牙 | 尚无实现 | 如需 BLE，单独实现 transport、认证、资源预算及真实设备验收；芯片支持不算适配完成 |

继续用 capability、资源配额和 host permissions 限制小组件访问。板级电源开关、Flash 分区和裸寄存器不因为增加一个设备而直接暴露给脚本。

## 5. 分层验证后再提升支持状态

1. **主机验证**：像素位序/长度/颜色、边界裁剪、驱动命令顺序、错误和超时清理、输入路由、配置与包校验。
2. **工具一致性**：同一设备描述和样例下，原生 Studio 与 WASM 预览像素和事件结果一致；未支持设备须明确拒绝。
3. **目标构建**：编译选定设备，核对镜像与分区、堆/栈/PSRAM 预算。构建通过不代表上板通过。
4. **授权后的实机验证**：先确认设备身份、备份与恢复条件，再按电源/按键 → RTC/电池 → 显示测试图 → 睡眠/唤醒 → 网络 → 可选音频/NFC 的顺序推进。未提供的外设记录为不适用，不能记作通过。
5. **记录与发布**：在设备 `history/` 写明 PCB、commit/工作树差异、电源来源、观测结果、BUSY 时序及有关电压/电流；区分 pass/fail 与未确认，更新支持矩阵和安装限制。

验证命令见[构建与验证](building.md)。完成驱动和构建后仍标“适配中”；只有完成所声明功能的实机验收，才把对应功能标为支持。每种板卡、显示变体和 revision 的结论分别记录。
