# Screen 自动差异窗口刷新

`canvas.flush().await` 的脚本接口不变：接收不可变画面快照后返回，由宿主选择是否刷新、全屏刷新或 PTLW 窗口刷新。脚本不用维护脏区域，也不用选择刷新类型。

## 选择规则

1. 保持现有固定 200ms 合并窗口；刷新中只保留最新待呈现帧。
2. 最终像素的 SHA-256 与最后一次刷新及安全清理均成功的画面一致时，报告 `unchanged`，不操作屏幕。
3. 存在同一前台代次的有效显示基线时，比较完整 30,000 B 2bpp 像素，取所有变化像素的单个包围窗口。横向向外对齐到 4 像素，纵向按实际变化行，坐标为 inclusive；不比较绘图指令，也不以尚未显示的提交作为基线。
4. 对齐后窗口小于全屏面积的 50%，且连续成功局刷少于 8 次时，使用 PTLW。红、黄、黑、白变化都参与比较。窗口可能包含少量未变化像素。
5. 无基线、不同前台代次、基线分配失败、窗口面积达到 50%，或者已经连续成功局刷 8 次时，采用全刷。相同像素仍优先跳过，不为凑次数刷新。

50% 与 8 次是软件保守策略，不是来自控制器 datasheet 的硬件极限或寿命保证。启动后第一幅变化画面使用全刷；诊断/状态页等其他入口改屏时使基线失效。前台切换、配置重建后的第一幅变化画面也全刷。

## 驱动、错误与内存

PTLW 复用既有 NOTE4C 实机验证过的指令顺序：初始化、参考兼容命令、**完整 30,000 B DTM**、启用窗口、PON/DRF、禁用窗口、断电/深睡及强制安全清理。不使用短窗口传输，不修改 LUT/MTP 或引入未公开命令。窗口限制刷新范围，**不承诺缩短约 20–25 秒的刷新等待**。

只有刷新和清理都成功，才更新显示基线。失败使基线失效并保留目标；不立即循环重试。下一次显式重试或新提交使用全刷重新建立基线。局刷次数也只有成功时才增加，全刷成功时归零。

四份 30,000 B 提交缓冲池保持不变；额外使用一份最多 30,000 B 的成功显示基线，总像素预算最多 150,000 B。所有像素显式分配在 PSRAM，元数据和同步对象留在内部 RAM。基线采用独立存储，避免持有池中第五种角色而使刷新期间的连续提交耗尽池；基线分配失败时仅停用自动局刷，仍能全刷。脚本源码、指令及 VM 内存配额未增加。

## 管理状态

`system.status` 和 `dashboard.get` 的 `presentation` 增加：

- `refresh_mode`: `full`、`partial` 或 null。
- `window`: 局刷时为 `{x, y, width, height}`，否则 null。

字段描述最新提交实际开始的刷新方式；新提交等待及相同像素跳过时为空。管理页同时显示刷新方式和区域尺寸。`presented` 仍表示物理刷新和清理完成，flush 返回不等于显示完成。

## 验证依据

首次中心黑白窗口的目视和时序证据见 [2026-09-02 Phase 1](history/phase1-hardware-log-2026-09-02.md#ssd2683-ptlw-局刷实验)。本次主机完整套件 171 项通过，新增覆盖四色像素差异、边缘/对齐、大面积回退、以实际成功帧为基线、刷新中替换目标、错误后全刷重试、周期全刷和 PTLW 错误/超时断电清理。

目标构建通过；最终应用镜像 3,731,760 / 4,128,768 B（90.38%），余量 397,008 B，保持现有分区和 app-only 流程。本次自动局刷的设备观测、用户目视反馈和恢复结果见 [2026-09-09 自动局刷实机记录](history/partial-refresh-hardware-log-2026-09-09.md)。不同窗口、温度和长期反复刷新不能由一次实验推定已验证。
